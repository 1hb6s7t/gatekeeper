# 守门人 Gatekeeper

> 长篇小说的设定与连续性核对工具。AI 不动笔，只做三件事：从已写章节**抽取**设定与时间线，对新章节**找矛盾**，每条结论**附原文证据**。

调研结论见 `docs/` 与上层目录的《AI 故事创作产品_市场调研报告》：欧美工具、中文网文、短剧编剧、学术基准在同一个地方失败，即长篇一致性；而所有网文平台都允许 AI 做大纲、人设、检查，禁止 AI 代写正文。守门人就切这一刀。

## 运行

```bash
pip install fastapi uvicorn anthropic
python -m uvicorn app.server:app --port 8765
# 打开 http://localhost:8765 ，点「载入示例」→「切分章节」→「建立设定库」→ 切到「新章节」→「检查矛盾」→「对照答案卡」
```

模型通道由环境变量决定：

| 变量 | 取值 | 说明 |
|---|---|---|
| `GATEKEEPER_PROVIDER` | `auto`（默认）/ `anthropic` / `claude-cli` / `cache` | `auto` 先试 Anthropic SDK，失败再试 `claude -p`；`cache` 只回放缓存 |
| `GATEKEEPER_MODEL` | 默认 `claude-opus-5` | Anthropic SDK 用的模型 |
| `GATEKEEPER_CLI_EFFORT` | 默认 `medium` | `claude -p --effort` |
| `GATEKEEPER_CLI_MODEL` | 可选 | `claude -p --model` |

Anthropic SDK 读标准的 `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_BASE_URL`。

## 评估

```bash
python eval.py            # 用缓存，秒级
python eval.py --no-cache # 真实调用模型
```

内置示例《青崖夜行》：5 章正文 + 预埋 10 处矛盾的第六章 + 2 个陷阱（不应报的地方）。答案卡在 `samples/answer_key.json`。评估输出召回、答案卡外发现数、引用逐字命中率。最近一次结果见下文「当前状态」。

## 唯一必须走通的用户路径

1. 粘贴已写章节，按「第 N 章」自动切分
2. 建立设定库：逐章抽取角色、地点、物品、时间线，每条事实带来源章节与逐字引用；引用会与原文比对，未命中的标黄
3. 粘贴新章，检查：矛盾清单，每条含类型、严重度、设定来源引用、新章冲突引用、一句话建议；点引用可在「原文」页高亮定位
4. 对每条：采纳 / 忽略 / 有意为之（写入项目记忆，下次检查时随 prompt 传入，不再报）
5. 确认后把新章并入稿件，继续抽取，设定库随连载增长

## 哪些是真实的，哪些是缓存，哪些没做

**真实可用**
- 切章、抽取、检查、证据校验、状态记忆、并入稿件、评估脚本，全部真实调用模型
- 两条模型通道：Anthropic 官方 SDK（流式，`claude-opus-5`）、`claude -p`（Claude Code 非交互模式）
- 引用校验是程序做的，不是模型说的：抽取的 quote 必须逐字出现在该章原文，检查的 conflict_quote 必须逐字出现在新章原文，否则界面标黄

**缓存**
- `data/cache/` 里存有内置示例 5 章抽取 + 第六章检查的模型原始输出，按 prompt 哈希命中。界面「来源」会显示「缓存」。取消勾选「允许使用缓存结果」即可强制重新调用
- 缓存只覆盖内置示例；粘贴自己的稿件一定走真实调用

**没做**
- 没有账号、数据库、多用户；项目存为 `data/projects/*.json`
- 没有对 30 万字以上稿件的分段策略；设定库整体随 prompt 传入，几十章后会撞上下文与费用
- 没有「采纳建议」后自动改写新章，采纳只是标记状态
- 短剧剧本模式（按集诊断冲突、爽点、集末钩子）没做，只在 PRD 里作为第二种文档类型
- `auto` 通道遇到中转站的模型限制时只会退到 `claude -p`，没有更多 provider
- 没有用官方 Anthropic 端点实测过 SDK 通道（见「当前状态」）

## 当前状态

最近一次真实调用（2026-09-09，通道 `claude -p`，`--effort medium`，模型 claude-opus-5），`python eval.py --no-cache`：

| 项目 | 结果 |
|---|---|
| 设定库 | 15 个实体，60 条事实，引用逐字命中 60/60 |
| 第六章检查 | 9 条发现，冲突引用逐字命中 9/9 |
| 预埋矛盾召回 | 9/10（漏 #10：黑袍人「左肩被刺穿」与第六章「身上一点伤都没有」，文中苏棠自己已质疑，属边缘案例） |
| 答案卡外的发现 | 1（林砚回忆周老头原话与第一章不符，人工复核是真矛盾，答案卡没覆盖） |
| 踩陷阱 | 0/2 |
| 耗时 | 抽取每章 60–240 秒，检查 86 秒 |

对照 PRD 成功标准：召回 ≥7 达标，误报 ≤3 达标，离线走通达标；「一次检查 60 秒内」在 `claude -p` 通道下**没有达标**（86 秒），走缓存时秒级。`python eval.py`（缓存）与界面「对照答案卡」给出相同数字。

已知环境限制：当前 `ANTHROPIC_BASE_URL` 指向的中转站拒绝 Anthropic SDK 的所有请求（400/503），所以 `auto` 实际总是退到 `claude -p`；换到官方端点即走 SDK 流式通道，代码路径已写好但未在官方端点上实测。

界面截图：`docs/shot1_chapters.png`（切章）、`shot2_bible.png`（设定库）、`shot3_findings.png`（矛盾清单）、`shot4_reader.png`（引用高亮）、`shot5_eval.png`（答案卡）。全路径由 Playwright 驱动无头 Chrome 走通，无 console 错误。

## 下一步优先级

1. 误报控制：区分真矛盾、有意伏笔、视角限制；「有意为之」目前是文本匹配，应改为结构化规则
2. 抽取召回：对比逐章增量抽取与全文一次抽取；对更新型事实（伤势、物品易手）单独建「状态变更」表
3. 规模：设定库按实体检索注入而不是整体注入；对 50 章以上稿件分卷
4. 剧本模式：按集拆分，检查角色出场连续性与卡点结构
